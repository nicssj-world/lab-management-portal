# Design Spec: โมดูลจุดรวมพล/แผนอพยพ

สถานะ: แบบออกแบบได้รับการเห็นชอบในบทสนทนาแล้ว — รอผู้ใช้ตรวจเอกสารก่อนจัดทำ implementation plan
วันที่: 23 สิงหาคม 2569
ขอบเขต: ระบบ Lab Management Portal

## 1. บริบทและหลักฐานอ้างอิง

ผู้ใช้ต้องการแยกงานด้านความปลอดภัยออกเป็น 3 โมดูลที่มีเจ้าของและวัตถุประสงค์ชัดเจน:

1. แผนที่ห้องปฏิบัติการ
2. อุปกรณ์ความปลอดภัย
3. จุดรวมพล/แผนอพยพ

เอกสารที่ใช้กำหนดขอบเขตของโมดูลนี้:

- `tmp/unsafe-manuals/QP-LAB-26.pdf` — QP-LAB-26 ความปลอดภัยในห้องปฏิบัติการ Rev.10 มีผลใช้วันที่ 8 มีนาคม 2569
- `tmp/unsafe-manuals/MN-LAB-02.pdf` — MN-LAB-02 คู่มือความปลอดภัยในห้องปฏิบัติการ Rev.9 มีผลใช้วันที่ 10 มีนาคม 2569

ประเด็นที่มีผลต่อการออกแบบ:

- QP-LAB-26 ข้อ 5.1.4.7 กำหนดให้ทบทวน QP-LAB-26 และ MN-LAB-02
- QP-LAB-26 ข้อ 5.2.3–5.2.4 กำหนดให้มีการอบรมและซ้อมแผนฉุกเฉินอย่างน้อยทุก 12 เดือน ครอบคลุมกรณีเพลิงไหม้ สารเคมีหกรั่วไหล CPR และเวลานอกเวลาราชการ
- QP-LAB-26 ข้อ 5.2.5 กำหนดให้ใช้แผนฉุกเฉินของโรงพยาบาลและรายงานเหตุการณ์ภายใน 24 ชั่วโมง
- QP-LAB-26 ตัวชี้วัดข้อ 6.6 ระบุอัตราซ้อมแผน 100% อย่างน้อยปีละครั้ง เวลาอพยพเฉลี่ยไม่เกิน 5 นาที ความสอดคล้องกับแผนอพยพอย่างน้อย 90% และความพร้อมของแผนสำรอง 100%
- MN-LAB-02 ข้อ 5.1.9 และ 5.8 กำหนดให้ติดผังทางหนีไฟ ใช้ทางออกที่ปลอดภัย รายงานตัวต่อ LSO/ผู้แทน และมีจุดรวมพลตามบริบทของพื้นที่ เช่น ห้องปฏิบัติการกลาง/จุลชีววิทยา จุดเชื่อมอาคารสำหรับคลังเลือด และจุดรับส่งผู้ป่วยสำหรับห้องปฏิบัติการผู้ป่วยนอก
- MN-LAB-02 กำหนดให้ LSO ตรวจนับคนและรายงานหัวหน้าห้องปฏิบัติการ ส่วนเหตุเพลิงไหม้ให้เชื่อมกับ HP-FMS-CBH-08 และแบบประเมินการซ้อมที่เกี่ยวข้อง

## 2. ปัญหาและเป้าหมาย

### ปัญหา

หน้าปัจจุบันรวมอุปกรณ์ความปลอดภัย จุดรวมพล และผู้รับผิดชอบไว้ในพื้นที่เดียวกัน ทำให้ผู้ใช้สับสนระหว่าง:

- ข้อมูลตำแหน่งถาวรบนแผนที่
- ข้อมูลจุดรวมพล/ทางอพยพที่ต้องอนุมัติและทบทวนเป็นรุ่น
- งานซ้อมแผนประจำปีและหลักฐานที่ต้องตรวจสอบ

นอกจากนี้ จุดรวมพลไม่ได้เป็นเพียงหมุดบนแผนที่ แต่เป็นส่วนหนึ่งของเส้นทางที่เริ่มจากพื้นที่ทำงาน ไปยังทางออก แล้วไปยังจุดรวมพล/จุดปลอดภัย พร้อมขั้นตอนนับคน รายงานตัว ประเมินผล และติดตาม CAPA

### เป้าหมาย

- แยกความรับผิดชอบของ 3 โมดูลโดยไม่ทำให้ข้อมูลแผนที่ซ้ำกัน
- จัดการแผนอพยพเป็นข้อมูลที่มีรุ่น สถานะ ผู้ทบทวน ผู้อนุมัติ และวันมีผล
- รองรับจุดรวมพล จุดปลอดภัย ทางออก และเส้นทางหลัก/สำรองตาม MN-LAB-02
- เชื่อมการทบทวนแผนและการซ้อมประจำปีกับ Quality Tasks เดิม
- เก็บหลักฐาน แสดงความครบถ้วน และสร้าง/ติดตาม CAPA โดยไม่สร้างระบบไฟล์ซ้ำ
- ให้ข้อมูลฉบับอนุมัติสำหรับพิมพ์ A3/A4 และเผยแพร่แบบอ่านอย่างเดียว โดยระบบออนไลน์ไม่เป็นแหล่งพึ่งพาเพียงแหล่งเดียวในเหตุฉุกเฉิน

## 3. ขอบเขตและเจ้าของข้อมูลของ 3 โมดูล

| โมดูล | ขอบเขตหลัก | ไม่ควรเป็นเจ้าของ |
| --- | --- | --- |
| แผนที่ห้องปฏิบัติการ | ผังพื้นที่ ห้อง จุดอ้างอิง ทางเดิน ทางออก และการนำทางบน floor plan | แบบฝึกซ้อม ผลนับคน หลักฐาน และสถานะอนุมัติแผนอพยพ |
| อุปกรณ์ความปลอดภัย | อุปกรณ์ เช่น ถังดับเพลิง ชุด spill kit ฝักบัว/อ่างล้างตา และรอบตรวจ | จุดรวมพล เส้นทางอพยพ และบันทึกการซ้อม |
| จุดรวมพล/แผนอพยพ | แผนอพยพ จุดรวมพล/จุดปลอดภัย การทบทวน แผนซ้อม ผลการซ้อม งาน และหลักฐาน | ทะเบียนอุปกรณ์ หรือ geometry หลักของ floor plan |

ความสัมพันธ์ระหว่างโมดูลให้ใช้รหัสและ foreign key ของข้อมูลแผนที่เดิม ไม่คัดลอก geometry ห้องหรือเส้นทางลงในโมดูลใหม่ จุดรวมพลสามารถแสดงบนแผนผังบริเวณ/แผนที่ไซต์ประกอบได้ แต่การจัดการและการอนุมัติอยู่ในโมดูลที่ 3

## 4. แนวทางที่พิจารณาและข้อเสนอแนะ

### แนวทาง A — ขยายระบบแผนที่ รุ่นแผนที่ และ Quality Tasks เดิม (แนะนำ)

เพิ่มโมดูลใหม่ที่ใช้ `lab_map_versions`, route presets, exits, assembly points และระบบ Quality Tasks/Evidence เดิมเป็นฐาน แล้วเพิ่ม entity เฉพาะของแผนอพยพและการซ้อม ข้อดีคือไม่สร้างทะเบียนแผนที่/ไฟล์/งานซ้ำ และบังคับใช้ release gate ที่มีอยู่ได้ ข้อแลกเปลี่ยนคือ schema และ workflow ต้องออกแบบให้เชื่อมหลายส่วนอย่างระมัดระวัง

### แนวทาง B — ใช้เอกสารหรือ PDF เป็นศูนย์กลาง

เก็บผังอพยพและรายงานซ้อมเป็นไฟล์ พร้อม metadata ขั้นต่ำ ข้อดีคือเริ่มต้นเร็วและใกล้เคียงวิธีทำงานเดิม ข้อเสียคือค้นหาจุดรวมพล/ทางออกไม่ได้เป็นโครงสร้าง วัดเวลาอพยพและความครบถ้วนของหลักฐานยาก และตรวจสอบความสัมพันธ์กับแผนที่ไม่ได้ จึงไม่เหมาะกับเป้าหมายระยะยาว

### แนวทาง C — รวมทุกอย่างไว้ใน Safety Center เดียว

ทำหน้าเดียวรวมแผนที่ อุปกรณ์ จุดรวมพล และซ้อมแผน ข้อดีคือลดการเปลี่ยนเมนู แต่ทำให้เจ้าของข้อมูลและ lifecycle ปะปนกัน ผู้ใช้แยก “อุปกรณ์ที่ต้องตรวจ” ออกจาก “แผนที่ที่ต้องอนุมัติ” ได้ยาก จึงไม่ตรงกับความต้องการให้แยก 3 โมดูล

ข้อเสนอแนะคือใช้แนวทาง A โดยรักษาเส้นแบ่งของโมดูลใน navigation และสิทธิ์การทำงาน แม้ข้อมูลภายในจะเชื่อมกัน

## 5. โครงสร้างประสบการณ์ผู้ใช้

เส้นทางภายในที่เสนอ: `/staff/lab-map/evacuation` สำหรับผู้ปฏิบัติงานที่มีสิทธิ์ ส่วนหน้าอ่านอย่างเดียวและ QR ใช้เฉพาะข้อมูล map release/evacuation plan ที่เผยแพร่แล้ว

หน้าโมดูลแบ่งเป็น 5 มุมมอง:

1. **ภาพรวม** — สถานะแผนที่เผยแพร่ แผนที่รอทบทวน จุดรวมพลที่ยืนยันแล้ว ความพร้อมของแผนซ้อมปีปัจจุบัน และหลักฐานที่ขาด
2. **แผนอพยพ** — เลือกพื้นที่/สถานี แสดงเส้นทางหลักและเส้นทางสำรอง ทางออก จุดรวมพล/จุดปลอดภัย และคำแนะนำหลังออกจากอาคาร
3. **จุดรวมพล** — จัดการจุดรวมพลและจุดปลอดภัย รายละเอียด GPS ทางออกที่เชื่อมโยง สถานะการตรวจสอบ ภาพยืนยัน และประวัติการยืนยัน
4. **แผนซ้อมประจำปี** — รอบปี แผนการซ้อมจริง ผู้เข้าร่วม เวลาอพยพ การนับคน ผลประเมิน ความเบี่ยงเบน CAPA และหลักฐาน
5. **งานและหลักฐาน** — มุมมองเชื่อมไปยัง Quality Tasks เดิม แสดงงานที่ต้องทำ สถานะ approval ข้อกำหนดหลักฐาน และ action items

### รายละเอียดหน้าสำคัญ

#### แผนอพยพ

- เลือกอาคาร/ชั้น/พื้นที่ต้นทาง
- แสดงทางออกและ route preset ที่อนุมัติแล้ว โดยแยก `primary` และ `alternate`
- แสดงจุดรวมพลหรือจุดปลอดภัยหลังออกจากอาคาร
- แสดงคำแนะนำเฉพาะพื้นที่ เช่น จุดเชื่อมอาคาร จุดรับส่งผู้ป่วย หรือจุดรายงานตัว
- แสดงผู้รับผิดชอบการนับคนและจุดรายงานตัว
- พิมพ์ A3/A4 พร้อมเลขรุ่น วันมีผล ผู้ทบทวน ผู้อนุมัติ QR และข้อความให้ยึดป้ายฉบับอนุมัติในพื้นที่

#### จุดรวมพล

- แยก `assembly` (จุดรวมพล) และ `safe` (จุดปลอดภัย/จุดรายงานตัว) ตามชนิดข้อมูลเดิม
- เก็บชื่อ รายละเอียด พิกัด สถานะ lifecycle และทางออกที่เกี่ยวข้อง
- ยืนยันตำแหน่งด้วย GPS ความแม่นยำ ผู้ตรวจ วันที่ หมายเหตุ และภาพประกอบ
- ห้ามใช้สีเป็นตัวบอกสถานะเพียงอย่างเดียว ต้องมีข้อความและไอคอน/สัญลักษณ์ร่วมด้วย

#### แผนซ้อมประจำปี

- แยก “รอบแผน” ออกจาก “กิจกรรมซ้อมจริง” เพื่อรองรับการเลื่อนหรือซ้อมมากกว่าหนึ่งครั้งในปีเดียว
- ระบุสถานการณ์ ขอบเขตพื้นที่/เส้นทาง วันเวลา ในเวลาราชการหรือนอกเวลาราชการ ผู้สังเกตการณ์ ผู้รับผิดชอบ และแผนฉบับที่ใช้
- บันทึกเวลาเริ่มอพยพ เวลาสิ้นสุด ระยะเวลา ผู้คาดว่าจะเข้าร่วม ผู้เข้าร่วมจริง นับครบ/สูญหาย/บาดเจ็บ จุดรายงานตัว และผลประเมิน
- เชื่อมข้อเบี่ยงเบนกับ action item/CAPA และงานที่ต้องติดตาม

### แนวทาง UI/การเข้าถึง

- ใช้ภาษาไทยเป็นหลักและใช้ Noto Sans Thai ตาม design system ของระบบ
- contrast สูง พื้นที่กดอย่างน้อย 44px รองรับ keyboard/focus ring และ responsive
- สถานะ loading, success, error และการบันทึกต้องมี feedback ที่ชัดเจน รวมถึง announcement สำหรับ screen reader ในจุดสำคัญ
- ลด animation ในหน้าที่เกี่ยวกับเหตุฉุกเฉิน และไม่ใช้สีสด/gradient เป็นแกนของความหมาย
- แผนที่และภาพต้องมีคำอธิบาย/alt text ที่สื่อสารทางเลือกได้ ไม่พึ่งพาการมองสีอย่างเดียว

## 6. แบบจำลองข้อมูลที่เสนอ

ส่วนนี้เป็นแบบจำลองเชิงออกแบบ ชื่อคอลัมน์อาจปรับตาม migration จริง แต่หลักการเชื่อมโยงต้องคงไว้

### ใช้ข้อมูลเดิม

- `lab_map_versions` และ map release/snapshot เป็นแหล่งอ้างอิงของผังที่เผยแพร่
- `lab_map_route_presets`/manifest routes เป็นแหล่งอ้างอิงเส้นทางที่อนุมัติ ไม่คำนวณเส้นทางสั้นที่สุดแบบสด
- `lab_map_assembly_points`, `lab_map_assembly_point_exits`, `lab_map_assembly_point_verifications` เป็นทะเบียนจุดและประวัติการตรวจสอบ
- `quality_tasks`, task instances, `quality_task_links`, `quality_task_evidence_requirements`, `quality_task_attachments` และ `quality_task_action_items` เป็นแหล่งงาน/หลักฐาน/CAPA เดิม

### ตาราง/ความสัมพันธ์ใหม่ที่เสนอ

#### `evacuation_plan_versions`

เก็บรุ่นของแผนอพยพ ไม่เก็บ geometry ซ้ำ:

- `id`, `plan_code`, `version_code`
- `status`: `draft`, `in_review`, `approved`, `published`, `retired`
- `map_release_id` หรือ `map_version_id`
- `effective_date`, `review_due_date`
- ผู้จัดทำ ผู้ทบทวน ผู้อนุมัติ พร้อม timestamps
- `report_point_id` และผู้รับผิดชอบการนับคน/รายงานตัว
- แหล่งอ้างอิงเอกสาร หมายเหตุ และ audit metadata

รุ่นที่เผยแพร่แล้วต้อง immutable การแก้ไขสาระสำคัญสร้างรุ่นใหม่

#### `evacuation_exit_assignments`

จับคู่บริบทของพื้นที่กับทางออกและปลายทาง:

- `plan_version_id`
- `scope_type`: `station`, `space`, `zone`
- `scope_code`
- `exit_code`
- `assembly_point_id` หรือ `safe_point_id`
- `route_kind`/ลำดับความสำคัญ เช่น primary/alternate
- `post_exit_instruction_th`
- ผู้รับผิดชอบและหมายเหตุ

โครงสร้างนี้รองรับ mapping ตาม MN-LAB-02 เช่น ห้องปฏิบัติการกลาง/โมเลกุล/จุลชีววิทยา จุดเชื่อมอาคารของคลังเลือด ห้องปฏิบัติการผู้ป่วยนอก และจุดรายงานตัวทั่วไป

#### `evacuation_drill_cycles`

เก็บรอบแผนซ้อมประจำปี:

- `fiscal_year`, `plan_version_id`
- `quality_task_instance_id` หรือ link ผ่าน `quality_task_links`
- ผู้รับผิดชอบ เป้าหมาย และวันครบกำหนด
- `status`: `planned`, `in_progress`, `awaiting_evidence`, `pending_review`, `completed`, `cancelled`

#### `evacuation_drill_sessions`

เก็บกิจกรรมซ้อมจริงหนึ่งครั้งหรือหลายครั้งในรอบเดียว:

- cycle และ scenario
- วันเวลา/ในเวลาราชการหรือนอกเวลาราชการ
- ขอบเขตพื้นที่และ route presets ที่ใช้
- จำนวนผู้คาดหมาย/ผู้เข้าร่วมจริง
- เวลาเริ่ม เวลาเสร็จ และระยะเวลาอพยพ
- จำนวนที่ตรวจนับ ขาดหาย บาดเจ็บ และจุดรายงานตัว
- ผู้สังเกตการณ์ ผลประเมิน ความเบี่ยงเบน และหมายเหตุเหตุการณ์

#### `evacuation_drill_evidence`

ตารางเชื่อม session กับ `quality_task_attachments` โดยกำหนดบทบาทหลักฐาน เช่น plan, attendance, evaluation, photo, incident/CAPA ไม่เก็บไฟล์ซ้ำ หากระบบเดิมรองรับการอ้างอิง session ใน attachment metadata อยู่แล้ว สามารถใช้ join แบบบางได้ แต่ต้องคงความสามารถในการตรวจว่าหลักฐานใดเป็นของการซ้อมครั้งใด

CAPA ให้ใช้ `quality_task_action_items` โดยระบุ source type/source id ของรอบหรือ session ไม่สร้าง action-item table ชุดใหม่

### จุดรายงานตัวกับจุดรวมพล

จุดรวมพล/จุดปลอดภัยยังใช้ `point_type` เดิม ไม่เพิ่มชนิดที่สามสำหรับ “จุดรายงานตัว” ให้เก็บความสัมพันธ์ `report_point_id` และผู้รับผิดชอบแยกต่างหาก เพราะจุดรายงานตัวอาจเป็นบทบาท/ตำแหน่งในกระบวนการ ไม่ใช่หมุดทางกายภาพชนิดใหม่

## 7. การเชื่อมกับงานและหลักฐาน

ใช้ Quality Tasks เป็นระบบต้นทางของกำหนดการ สถานะ approval และไฟล์หลักฐาน แล้วให้โมดูลนี้เป็นมุมมอง domain ที่มีข้อมูลเฉพาะของแผนและผลการซ้อม

การ mapping ที่เสนอ:

| งานเดิม | การใช้งานในโมดูล |
| --- | --- |
| `CBH-ST-15` ทบทวน QP-LAB-26 และ MN-LAB-02 | เชื่อมกับการทบทวน/ต่ออายุ evacuation plan version |
| `CBH-ST-17` ซ้อมแผนฉุกเฉินประจำปี | เชื่อมกับ `evacuation_drill_cycles` และ session ผลการซ้อม |
| `CBH-ST-21` ทบทวนแผนฉุกเฉินงานคลังเลือด | เชื่อมกับ sub-plan หรือ scope ของ blood bank |
| `CBH-QT-33` Fire Drill | ไม่สร้างซ้ำ เนื่องจาก inactive และไม่ควรทำให้เกิดงานซ้ำ |

ควรขยายค่า `integration_kind` อย่างมี migration/constraint ที่ชัดเจน เช่น `evacuation_plan_review` และ `evacuation_drill` โดยต้องรักษา idempotency ของ `quality_task_links` และใช้ source id ที่ตรวจสอบย้อนกลับได้

ข้อกำหนดหลักฐานของ `CBH-ST-17` ปัจจุบันมีแผน/รายชื่อผู้เข้าร่วม ผลประเมิน และภาพการซ้อมในและนอกเวลาราชการ ควรรักษารายการเดิมและเพิ่ม/แยก requirement “หลักฐานการเข้าร่วม/การนับคน” ให้ตรวจความครบถ้วนได้ชัดเจน โดยไม่ลบหรือย้ายไฟล์เดิมโดยอัตโนมัติ

Check-in เดิมใช้กับผู้ใช้ที่เข้าสู่ระบบได้ สำหรับผู้เข้าร่วมภายนอกให้ใช้แบบบันทึก/ไฟล์หลักฐานหรือรายการ manual ที่มีผู้รับผิดชอบรับรอง ข้อมูลส่วนบุคคลของผู้เข้าร่วมไม่ควรปรากฏใน public map/QR view

## 8. Workflow และสถานะ

```text
เผยแพร่ map release
        |
        v
กำหนดจุดรวมพล + ทางออก + route preset หลัก/สำรอง
        |
        v
จัดทำ evacuation plan version
        |
        v
ทบทวน -> อนุมัติ -> เผยแพร่
        |
        v
สร้างรอบงานซ้อมประจำปีจาก Quality Task
        |
        v
บันทึก session: สถานการณ์/ผู้เข้าร่วม/เวลา/นับคน
        |
        v
แนบหลักฐาน + ผลประเมิน + สร้าง CAPA เมื่อมีข้อเบี่ยงเบน
        |
        v
ตรวจงาน/อนุมัติหลักฐาน -> ปิดรอบ -> ใช้ผลเป็นข้อมูลทบทวนรุ่นถัดไป
```

การเปลี่ยนแผนที่ ทางออก จุดรวมพล หรือ route preset ที่มีผลต่อเส้นทางต้องทำให้แผนเดิมเข้าสู่การทบทวนหรือสร้างรุ่นใหม่ ไม่แก้ทับข้อมูลที่เผยแพร่แล้ว

## 9. กฎความปลอดภัยและ fail-closed

- Public/QR view แสดงเฉพาะ map release และ evacuation plan ที่ `published` และมีวันมีผลเท่านั้น
- Draft/in-review/ข้อมูลภายในต้องไม่ถูกส่งออก public API และควรมี watermark ในหน้าพิมพ์ภายใน
- ห้ามเผยแพร่เมื่อจุดที่อ้างอิงยังไม่ยืนยัน ไม่มี GPS/ภาพตามเกณฑ์ ไม่มีทางออกที่เชื่อมโยง หรือ route preset ไม่ครบ
- ทุกต้นทางที่กำหนดต้องมี primary และ alternate ตามขอบเขตที่อนุมัติ และต้องมีปลายทางหลังออกจากอาคาร
- ห้ามใช้เส้นทางที่ผ่านลิฟต์โดยสารหรือประตู/ทางออกที่ล็อกถาวรตามข้อมูลความปลอดภัย
- ต้องมี report point และผู้รับผิดชอบการนับคน/รายงานตัวก่อน approve
- reviewer และ approver ต้องไม่ใช่บุคคลเดียวกันเมื่อ policy ของระบบกำหนดการแบ่งหน้าที่
- ไม่คำนวณ shortest path แบบสดในเหตุฉุกเฉิน ให้ใช้ route preset ที่ได้รับการทบทวนแล้ว
- เอกสารพิมพ์ A3/A4 ต้องมีแผนที่แบบคงที่ ชื่อจุด/คำแนะนำ วันมีผล รุ่น ผู้ทบทวน ผู้อนุมัติ และ QR สำหรับข้อมูลเสริม ไม่พึ่งพา Google Maps หรือเครือข่ายในการตัดสินใจหน้างาน
- เมื่อแผนที่หรือจุดรวมพลเปลี่ยน ต้องมี audit trail และการตรวจผลกระทบต่อ plan version/งานซ้อม

## 10. การแสดงผลสาธารณะและงานพิมพ์

พื้นผังห้องยังแสดงเส้นทางจากพื้นที่ต้นทางไปยังทางออก ส่วนข้อมูลหลังออกจากอาคารให้แสดงเป็น panel แผนที่บริเวณ/แผนที่ไซต์แบบ static ซึ่งมีจุดรวมพล จุดปลอดภัย และคำแนะนำการรายงานตัว ไม่พยายามวางจุดรวมพลนอกอาคารลงบนพิกัดเดียวกับ floor plan หากไม่ใช่พิกัดภายในอาคารเดียวกัน

หน้า public ควรแสดงอย่างน้อย:

- แผนฉบับที่ใช้และวันมีผล
- จุดรวมพล/จุดปลอดภัยที่เกี่ยวข้องกับทางออก
- คำแนะนำ “ไปจุดรวมพลและรายงานตัวต่อ LSO/ผู้แทน” ตามบริบท
- ข้อความเตือนให้ปฏิบัติตามป้ายฉบับอนุมัติในพื้นที่

ไม่แสดงรายชื่อผู้เข้าร่วมซ้อม รายละเอียดบุคลากรภายใน เหตุการณ์ที่ยังไม่ปิด หรือหลักฐานส่วนตัวบนหน้า public

## 11. ตัวชี้วัดและรายงาน

โมดูลควรสรุปตัวชี้วัดจากข้อมูลเชิงโครงสร้างและ Quality Tasks:

- อัตราการซ้อมแผนประจำปีครบถ้วน 100%
- เวลาอพยพเฉลี่ยไม่เกิน 5 นาที
- ความสอดคล้องกับ route/evacuation plan อย่างน้อย 90%
- ความพร้อมของจุดรวมพล ทางออก และแผนสำรอง 100%
- อัตราหลักฐานครบตาม requirement ของงาน
- จำนวนข้อเบี่ยงเบน/CAPA ที่ค้างและอายุของงาน
- จำนวน plan version ที่ใกล้ครบกำหนดทบทวน

ผลลัพธ์ควร drill down จากตัวเลขไปยัง plan version, task, session และหลักฐานที่เป็นต้นทางได้

## 12. เกณฑ์ยอมรับและการทดสอบ

### Domain และข้อมูล

- สร้าง plan version พร้อม primary/alternate และปลายทางได้โดยไม่คัดลอก geometry แผนที่
- รองรับ mapping พื้นที่ตาม MN-LAB-02 รวม blood bank และ outpatient lab
- จุดรวมพล/จุดปลอดภัยที่ยังไม่ verify ไม่สามารถเป็นส่วนหนึ่งของแผนที่เผยแพร่
- การเปลี่ยนแปลง map release/route/point สร้างผลกระทบหรือบังคับ re-review อย่างตรวจสอบได้

### Workflow และ integration

- สร้าง/เชื่อมงาน `CBH-ST-15`, `CBH-ST-17`, `CBH-ST-21` ได้แบบไม่สร้าง link ซ้ำ
- สถานะ task และสถานะ cycle/session สอดคล้องกันเมื่อมีการส่งตรวจ อนุมัติ หรือยกเลิก
- ระบบตรวจ requirement หลักฐานครบก่อนปิดรอบตาม approval policy
- ผลเบี่ยงเบนสร้างและติดตาม action item/CAPA จาก source ที่ถูกต้อง

### Public/print และความปลอดภัย

- public projection ไม่ส่ง draft, ข้อมูลบุคคล, หลักฐานภายใน หรือแผนที่หมดอายุ
- งานพิมพ์แสดง version/effective date/reviewer/approver และข้อมูลจุดรวมพลครบ
- เมื่อ route หรือ point ไม่พร้อม ระบบแสดงข้อผิดพลาดที่แก้ไขได้และไม่ให้ publish
- ตรวจ responsive, keyboard navigation, focus, contrast, screen-reader labels และ reduced motion

### Regression

- แผนที่ห้องปฏิบัติการและโมดูลอุปกรณ์ความปลอดภัยยังทำงานแยกจากโมดูลนี้ได้
- map release เดิมและ route preset เดิมไม่เปลี่ยนผลโดยไม่ตั้งใจ
- งาน/หลักฐาน safety เดิมที่ไม่ใช่ evacuation ยังแสดงและทำงานตามเดิม

## 13. นอกขอบเขต

- ไม่สร้างทะเบียนอุปกรณ์ความปลอดภัยใหม่ในโมดูลนี้
- ไม่สร้าง geometry หรือระบบวาด floor plan ชุดใหม่
- ไม่คำนวณเส้นทางที่สั้นที่สุดแบบ real-time
- ไม่ทำ live location, headcount tracking แบบเรียลไทม์ หรือการยืนยันตัวบุคคลภายนอกแบบสาธารณะ
- ไม่แทนที่นโยบาย/แผนฉุกเฉินระดับโรงพยาบาล เช่น HP-FMS-CBH-08
- ไม่สร้างระบบ task, file storage หรือ CAPA ซ้ำกับ Quality Tasks เดิม
- ไม่ให้ผู้ใช้ public แก้ไขแผนหรือจุดรวมพล

## 14. ลำดับการทำงานระดับสูงหลังอนุมัติสเปก

1. ออกแบบ migration, constraints, permission และ integration contract กับ map release/Quality Tasks
2. ทำ domain validation และ workflow ของ plan version, assembly point mapping และ drill cycle/session
3. ทำ staff UI แยก 3 โมดูล พร้อม task/evidence view
4. ทำ public/QR projection และ A3/A4 print จากรุ่นที่เผยแพร่
5. เพิ่ม tests, seed/mapping งานเดิม และตรวจข้อมูลจริงก่อนเปิดใช้

รายละเอียดระดับไฟล์ ชื่อตารางจริง และลำดับ migration จะจัดทำเป็น implementation plan หลังผู้ใช้ตรวจ Design Spec ฉบับนี้แล้ว
