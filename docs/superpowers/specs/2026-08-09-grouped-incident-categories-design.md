# จัดกลุ่มประเภทเหตุการณ์ในแบบรายงานอุบัติการณ์

วันที่: 2026-08-09

## เป้าหมาย

ปรับฟอร์มที่ `/staff/risk/report` จากรายการประเภทเหตุการณ์แบบ `<select>` เดียว ให้เป็นกลุ่มที่กดเปิด/ยุบได้ เพื่อให้เจ้าหน้าที่ค้นหาประเภทที่ใกล้เคียงได้เร็วขึ้น โดยเฉพาะรายการความคลาดเคลื่อนด้านการใช้เลือดที่มีหลายรายการคล้ายกัน

## ขอบเขต

เปลี่ยนเฉพาะข้อมูลตัวเลือกและ UI ของ `IncidentReportForm`:

- เพิ่มกลุ่มประเภทเหตุการณ์ 7 กลุ่ม
- ให้เปิดได้หลายกลุ่มพร้อมกัน
- ใช้ radio จริงภายในกลุ่ม เลือกได้หนึ่งรายการ
- คงค่า `event_category` เป็น string เดิมใน payload
- ไม่เปลี่ยน API, validation schema, database หรือโครงสร้างข้อมูลที่จัดเก็บ

ไม่ทำการเพิ่มช่องค้นหา, เปลี่ยนข้อความรายการเดิม, หรือปรับปรุงหน้าทะเบียนอุบัติการณ์ในงานนี้

## กลุ่มและรายการ

### 1. สิ่งส่งตรวจ/การรับตัวอย่าง

- สิ่งส่งตรวจ Hemolysis
- สิ่งส่งตรวจ Turbid
- สิ่งส่งตรวจ clot
- สิ่งส่งตรวจปริมาตรไม่เพียงพอสำหรับการทดสอบ
- สิ่งส่งตรวจผิดชนิด หรือ ใส่ภาชนะผิดชนิด
- ตัวอย่างไม่ครบตามใบส่งตรวจ
- สิ่งส่งตรวจหก - แตก เลอะ

### 2. การระบุตัวตน/ใบส่งตรวจ

- ชื่อใบนำส่งตรวจกับสิ่งส่งตรวจไม่ตรงกัน
- เก็บสิ่งส่งตรวจผิดราย
- Request ผิดราย
- ติด Barcode ผิดราย
- ไม่ติดชื่อสกุลบนภาชนะที่ส่งตรวจ

### 3. การขนส่ง/กระบวนการ

- ไม่ได้รับสิ่งส่งตรวจ
- ส่งสิ่งส่งตรวจเกินระยะเวลาที่กำหนด

### 4. ระบบ/วัสดุ/อื่นๆ

- ระบบ LIS ขัดข้อง
- ระบบ HIS ขัดข้อง
- Reagent หมดอายุ
- อื่นๆ

### 5. คำสั่งการใช้เลือดคลาดเคลื่อน

- สั่งเลือด/ส่วนประกอบเลือดผิดจำนวน
- สั่งเลือด/ส่วนประกอบเลือดผิดชนิด/ไม่ตรงชนิด
- สั่งเลือด/ส่วนประกอบเลือดผิดคน

### 6. การจ่ายเลือดคลาดเคลื่อน

- จ่ายเลือด/ส่วนประกอบเลือดล่าช้า
- จ่ายเลือด/ส่วนประกอบเลือดผิดจำนวน/ชนิด
- จ่ายเลือด/ส่วนประกอบเลือดผิดคน

### 7. การบริหารเลือดคลาดเคลื่อน

- ไม่ให้เลือด/ส่วนประกอบเลือด
- เกิดปฏิกิริยาหลังให้เลือด
- เกิดปฏิกิริยาหลังให้เลือดรุนแรง
- ให้เลือดผิดหมู่

## การออกแบบข้อมูล

เพิ่มแหล่งข้อมูลหลัก `INCIDENT_CATEGORY_GROUPS` ใน `components/risk/shared/tokens.ts` โดยแต่ละกลุ่มมี `id`, `label` และ `items` แบบ readonly

`INCIDENT_CATEGORIES` จะยังคงมีไว้เป็นรายการแบบแบนที่สร้างจาก `INCIDENT_CATEGORY_GROUPS` เพื่อรักษา interface เดิมและให้แน่ใจว่ารายการที่ใช้ใน UI/validation มาจากแหล่งเดียวกัน รายการทั้งหมดต้องไม่ซ้ำกันและมี 28 รายการ (เดิม 18 + ใหม่ 10)

เพิ่ม helper แบบ pure สำหรับค้นหากลุ่มจากค่า `event_category` เพื่อใช้เปิดกลุ่มอัตโนมัติและทดสอบได้โดยไม่ต้องพึ่ง React หรือ Supabase

## การทำงานของฟอร์ม

ใน `components/risk/IncidentReportForm.tsx`:

1. ฟอร์มเริ่มต้นด้วยทุกกลุ่มยุบ
2. state ของฟอร์มยังคงใช้ `draft.event_category` เป็น string เดิม
3. state ใหม่เก็บกลุ่มที่เปิดอยู่เป็น set/list ของ group id ทำให้เปิดได้หลายกลุ่ม
4. หัวกลุ่มเป็น `button type="button"` เต็มพื้นที่ พร้อม `aria-expanded` และ `aria-controls`
5. เมื่อเปิดกลุ่ม จะแสดง radio ที่ใช้ `name="event_category"` ร่วมกันทั้งหมด
6. เมื่อเลือก radio จะอัปเดต `draft.event_category` เหมือนเดิม และเปิดกลุ่มนั้นค้างไว้
7. เมื่อกู้ร่างจาก Local Storage หากมี category ที่อยู่ในกลุ่ม ระบบจะเปิดกลุ่มนั้นอัตโนมัติ
8. เมื่อ submit ไม่ผ่าน validation ประเภทเหตุการณ์ ระบบจะเปิดกลุ่มแรกและโฟกัสหัวกลุ่ม เพื่อให้ผู้ใช้ไปเลือกได้ทันที
9. request body ที่ส่งไป `/api/admin/risk/incidents/report` ไม่เปลี่ยนแปลง

หัวกลุ่มที่มีรายการถูกเลือกจะแสดงสถานะ “เลือกแล้ว” และชื่อรายการที่เลือก ส่วน radio ที่เลือกจะแสดงพื้นหลัง/เส้นขอบและไอคอนตรวจสอบร่วมกับข้อความ ไม่สื่อความหมายด้วยสีอย่างเดียว

## Accessibility และ responsive behavior

- ใช้ native button และ native radio เพื่อรองรับ Tab, Space และการเลือกด้วยคีย์บอร์ด
- เพิ่ม label/aria attributes ให้หัวกลุ่มและรายการสัมพันธ์กัน
- ปุ่มและรายการมีพื้นที่กดอย่างน้อย 44px
- ใช้ focus-visible outline ที่มองเห็นได้
- แสดง validation error ใต้หัวข้อประเภทเหตุการณ์ด้วย `role="alert"`
- รักษาการแสดงผลบนมือถือด้วย layout แนวตั้งและข้อความที่ตัดบรรทัดได้
- ไม่พึ่งสีเพียงอย่างเดียว และไม่เพิ่ม motion ที่จำเป็นต่อการใช้งาน

## ความเข้ากันได้และข้อผิดพลาด

- ค่า category เดิมทั้ง 18 รายการยังอยู่ในรายการใหม่และส่งเป็นค่า string เดิม
- validation `event_category` ยังคงบังคับให้เลือกหนึ่งรายการตาม schema เดิม
- การกู้ร่างยังใช้ key เดิม `risk.incident-report.draft`
- ไม่เปลี่ยน behavior ของการบันทึกร่าง, การส่งรายงาน, หรือการล้างฟอร์ม

## แผนการทดสอบ

ทำตาม TDD โดยเพิ่มการทดสอบก่อน implementation:

- ทดสอบว่ามีครบ 7 กลุ่มและ label ตรงตาม spec
- ทดสอบรายการใหม่ด้านเลือดครบ 10 รายการและข้อความตรงตามที่กำหนด
- ทดสอบว่า flatten กลุ่มได้รายการครบ 28 รายการและไม่มีค่าซ้ำ
- ทดสอบ helper ที่ค้นหากลุ่มจาก category และกรณีไม่พบค่า
- รัน test ที่เพิ่มให้เห็น failure ก่อนเขียน implementation จากนั้นรันซ้ำให้ผ่าน
- รัน `npm run build` เพื่อตรวจ TypeScript และ Next.js integration
- ตรวจด้วย acceptance checklist: ทุกกลุ่มเริ่มยุบ, เปิดหลายกลุ่มได้, เลือกได้หนึ่งรายการ, เปิดกลุ่มที่เลือกตอนกู้ร่าง, validation เปิดกลุ่มให้แก้ได้ และ submit ส่งค่าเดิม
